## Peak memory vs input size (warm median)

Peak RSS = a fixed **~115 MiB JVM/PDFBox/AWT floor** + the document held in
heap. The floor dominates small inputs (so `RSS/size` looks huge and then
falls); for large inputs the marginal RSS settles to **roughly the input
size** — that is the output document's memory-only stream cache accumulating
every cloned page stream until save. Extrapolating that slope against the
launcher heap locates the input size at which it would OOM: the cliff this
benchmark exists to find. (Max-RSS is GC-timing sensitive, so small inputs
can read at or near the bare floor.)

| Input | Pages | Size (MiB) | Peak RSS (MiB) | RSS/size |
|---|---:|---:|---:|---:|
| sample.pdf | 4 | 0.0 | 115 | — |
| 省察.pdf | 102 | 4.6 | 147 | 32.1× |
| テキスト4_ヒューム『人間知性研究』.pdf | 118 | 5.3 | 116 | 21.7× |
| アンリ・ベルクソン『直接意識に与えられたものについての試論』.pdf | 316 | 34.6 | 167 | 4.8× |
| 森正人『誰が場所をつくるのかポストヒューマニズム的試論』.pdf | 343 | 52.8 | 184 | 3.5× |

## Memory safety

Two defences keep the heap from being exhausted by a very large scan:

1. **RAM-proportional heap** — the launcher runs with
   `-XX:MaxRAMPercentage=75.0` (see `build.gradle.kts`), so the heap scales
   to the host and honours container cgroup limits instead of a fixed 2g.
2. **`--low-memory`** — spills cloned page streams to a temp file
   (`java.io.tmpdir`) via PDFBox's scratch stream cache, bounding heap
   regardless of input size, at the cost of some disk I/O.

Verified on the largest sample under a deliberately tiny heap: with
`JAVA_TOOL_OPTIONS=-Xmx64m` the default (in-memory) conversion exits 137
(OutOfMemory), while the same conversion with `--low-memory` completes
successfully and produces an identical page count. Note that if
`java.io.tmpdir` is a tmpfs (RAM-backed), `--low-memory` does not free
physical memory — point it at real disk on memory-constrained hosts.
